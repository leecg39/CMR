# 서버 기록·고객사 격리 PoC

검증일: 2026-10-01, Asia/Seoul. 로컬 합성 데이터로 실행한 결과이며 실제 고객 운영과 실문자 전송을 검증한 결과는 아니다.

사용자 요청에 따라 문자·080 실연동과 파일럿 검증은 후속 작업으로 미뤘다. 이번 마무리는 설치 확인·로컬 서버 기록과 고객사 격리·동의 코어·최신 웹 CMP·복구 PoC 및 후속 출시 문서까지다.

## 개발 순서와 현재 관문

개발 순서는 **설치·버전 확인 → 서버 기록·고객사 격리 PoC → 동의 코어·웹 CMP → 문자·080 연동 → 제한 출시**를 따른다. 다음 단계의 개발은 가능하지만, 앞 단계의 실패를 남겨 둔 채 출시 관문을 통과했다고 표시하지 않는다.

| 단계 | 이번에 확인한 사실 | 남은 검증 |
|---|---|---|
| 설치·버전 확인 | Node.js 22.23.1, npm 10.9.8, PostgreSQL 17.11. 설치된 의존성 목록 확인, TypeScript 검사·빌드 실행 | 운영 Linux와 배포 환경에서 같은 검증 |
| 서버 기록·고객사 격리 PoC | 비소유자 DB 역할, 28개 고객사 테이블의 FORCE RLS, 실제 HTTP, 서버 재시작 후 원본 기록 유지 | 운영 저장소 장애·복제·백업 복원 훈련 |
| 동의 코어·웹 CMP | 실제 PostgreSQL 자동 테스트와 Ego Lite 웹 선택 검증 | 고객 사이트별 GTM·직접 실행 태그·로그인 뒤 경로 검증 |
| 문자·080 연동 | 모의 HTTP 계약, 페이지 순환·실패·접수 불명·중복 전송 방지 테스트 | SOLAPI 계정·등록 발신번호·080 계약·허가된 시험 수신번호의 왕복 검증 |
| 제한 출시 | 출시 조건과 실패 시 대응을 문서화 | [제한 출시 관문](LIMITED_RELEASE.md)의 실제 증거 확보 |

## 소스에서 확인한 구현

- `packages/database/schema.sql`과 마이그레이션은 고객사 테이블에 ENABLE/FORCE RLS, 복합 외래키, 멱등 키와 불변 원장 트리거를 정의한다.
- `packages/database/index.ts`는 트랜잭션 안에서 고객사 범위를 설정하고 고객사별 잠금을 얻는다. API와 워커의 시작 검사에서 슈퍼유저·BYPASSRLS·고객사 테이블 소유자 권한·FORCE RLS 누락을 거부한다.
- `apps/api/web.ts`는 검증된 사이트의 Origin과 서명 세션을 확인하고 서버 기록 성공 후 선택을 반환한다.
- `packages/web-sdk/cmp.js`는 기본 거절 신호를 먼저 보내고, 서버가 반환한 허용 목적의 등록 태그만 실행한다. 이미 실행된 스크립트의 효과는 새 페이지를 열어 확인해야 한다.

이는 코드로 확인한 사실이다. 아래 실행 증거와 범위를 구분해서 읽는다.

## 실제 실행한 HTTP·DB 검증

`npm run poc`는 작업 DB를 사용하지 않는다. 임시 `cmp_poc_*` DB와 비소유자 역할을 만들고, 별도 API 프로세스에 실제 HTTP 요청을 보낸 뒤 DB와 역할을 정리한다. 문자 실발송은 비활성화하고 합성 고객사 두 곳을 사용한다.

| 검사 | 합격 조건 |
|---|---|
| 런타임 역할·스키마 | 모든 고객사 테이블이 ENABLE/FORCE RLS이고 앱이 소유하지 않음 |
| 잘못된 실행 계정·스키마 | 고객사 테이블 소유자 또는 FORCE RLS 누락이면 API 프로세스가 시작 전에 종료 |
| 동일 식별자·번호 | 두 고객사의 외부 ID와 번호가 같아도 독립 주체, 서로 다른 HMAC·암호문 |
| DB 격리 | 고객사 A에서 B의 조회 0건, 교차 쓰기와 외래키 참조 거부, 풀 재사용 후 범위 미유출 |
| 트랜잭션 실패 | 철회 처리 중 오류를 주입하면 이벤트·상태·거부·통지·outbox·감사 기록 전부 이전 상태 유지 |
| 실제 HTTP 준비 상태 | PostgreSQL 연결 성공, 운영 모드에서는 데모 경로 404 |
| HTTP 격리·권한 | 양방향 교차 증빙·회원·수정 404, 읽기 키로 수정 403, 본문 고객사 변조 400 |
| 동시 재전송 | 같은 요청 8건이 원장 이벤트 1건과 처리결과 통지 1건만 생성 |
| 불변 원본 | 원장·게시 문구·감사 기록의 직접 UPDATE/DELETE 6건 모두 DB에서 거부 |
| 재시작과 증빙 | API 프로세스를 종료·재시작해도 이벤트 ID·서버 수신 시각·순서·철회 상태·원문 문구 유지, SHA-256 재계산 일치, 다른 고객사의 동의 유지 |

기본 HTTP 실행 결과는 `artifacts/poc/http-only/http.json`, API 로그는 같은 폴더의 `api.log`, 합성 증빙은 `synthetic-evidence.json`이다. 아래 복구 실행은 최신 소스에서 기본 10개 검사도 다시 포함한다. 결과에는 실행 시점 소스 지문과 환경, 검사별 상태, 임시 DB 정리 상태가 포함된다.

## 전체 DB 암호화 백업·복원 검증

`npm run poc:recovery`는 기본 10개에 복구 검사 3개를 추가한다. 실제 `pg_dump`/`pg_restore` 17.11로 합성 DB의 public 테이블 33개를 별도 새 DB에 복원하고, 모든 테이블의 행 수와 정렬된 행 지문이 일치하는지 확인했다. 덤프는 메모리에서 AES-256-GCM으로 암호화하며 평문 덤프 파일을 만들지 않는다. 암호문 변조와 다른 키로 복호화는 거부됐다.

복원한 API는 기존 비소유자 역할로 시작했고, 양방향 교차 증빙은 404, 원장 UPDATE는 DB 거부, 연락처 암호문은 같은 마스터 키로 복호화됐다. 백업 이후의 삭제를 별도 서명 이력으로 재적용하면 연락처 암호문 제거·예약 취소·새 광고 판단 차단이 확인됐다.

초기 복원에서는 재적용 후 다음 삭제 이력 내보내기가 빈 목록이 되어 과거 삭제를 잊는 문제가 재현됐다. `packages/evidence/recovery.ts`가 복원 DB의 삭제 원장에도 이력을 보존하도록 수정했으며, 같은 이력을 두 번 적용해도 삭제 원장은 1건이었다. 수정 전 실패는 `artifacts/poc/recovery-repro/http.json`, 수정 후 총 13개 통과는 `artifacts/poc/recovery/http.json`, 테이블별 지문은 `backup-table-fingerprints.json`에 있다.

시험 백업 키는 메모리에만 두고 복원 검사 후 폐기한다. 남은 `synthetic-backup.enc`는 시험 산출물이며 운영 복구용 백업이 아니다. 실제 운영에서는 별도 매체, 마스터·서명·백업 키의 안전한 복구, 객체 저장소·복제·담당자 대응까지 검증해야 한다. 시험의 원본 DB·복원 DB·앱 역할은 종료 시 모두 제거됐다.

## 격리 스캐너 컨테이너 검증

별도 Lima Linux 환경에서 Docker 29.8.2, Compose 5.5.1, Chromium 153.0.8010.12로 실행했다. `scripts/scanner-poc.mjs`의 7개 검사는 실제 컨테이너 자원·격리망, UID 1001·capabilities 없음·읽기 전용 루트·앱 비밀값 미전달, 직접 공인 IP 연결 거부, 프록시 공인 HTTPS 허용, 사설/메타데이터/비443/IPv6 대상 거부, Chromium sandbox·renderer·HTTPS, 내부 및 호스트 API 인증을 확인했다. SDK가 없는 example.com은 설치 성공으로 표시되지 않고 5개 시나리오 모두 실패로 반환됐다.

초기 실행에서는 seccomp의 capability 조건부 chroot가 거부되었고, 내부 격리망에만 연결한 컨테이너의 호스트 포트가 매핑되지 않았다. 전자는 namespace 안의 syscall 허용으로, 후자는 고정된 내부 주소로만 전달하는 별도 인증 게이트웨이로 수정했다. 수정 후 같은 환경에서 다시 실행해 통과했다. 운영 조건과 재현 명령은 [운영 안내](OPERATIONS.md)에 있다. 결과 원본은 `artifacts/poc/scanner.json`, 초기 실패 기록은 `scanner-sandbox.log`, 수정 후 기록은 `scanner-sandbox-fixed.log`에 있다.

고객사의 공개 사이트에 SDK를 설치한 상태의 컨테이너 비교 검증은 아직 하지 않았다. 위 실행 결과는 스캐너 런타임의 격리·실행·오류 표시를 검증한 것이다.

## 재실행

```sh
npm run build
npm test
npm run poc
npm run poc:recovery
# 브라우저 검증용 API를 유지하려면:
npm run poc -- --browser
```

`--browser`는 출력한 BROWSER_URL을 사용한다. 검증 후 Enter를 보내거나 출력된 PoC PID에 SIGUSR2를 보내면 서버 원본을 검사하고 임시 환경을 정리한다. 20분 타임아웃과 중단 시에도 정리를 시도한다. 경로를 분리하려면 `CMP_POC_OUTPUT=artifacts/poc/<실행명>`을 지정한다. PostgreSQL 관리자 소켓과 역할·DB 생성 권한이 필요하며, 앱 자체 검증은 새 비소유자 역할로 수행한다.

`scripts/verify-web.mjs`는 승인된 기존 Ego Lite TaskSpace와 위 브라우저 PoC 폴더를 받아 16개 검사를 실행한다. 새 공간을 만들지 않으며 로컬 127.0.0.1의 합성 데모만 대상으로 한다. 해당 공간과 서버가 실행 중일 때 다음과 같이 재검증한다. 숫자와 폴더는 실제 생성된 값으로 지정한다.

```sh
ego-browser nodejs -e 'const {verifyWeb}=await import("file:///Users/user01/Desktop/CMP/scripts/verify-web.mjs");await verifyWeb(taskSpace,{space:11,output:"/Users/user01/Desktop/CMP/artifacts/poc/web"});'
```

## 실패 시 대체 설계와 재검증 조건

아래는 실패할 때 적용할 설계 제안이며 현재 구현을 이미 변경했다는 뜻은 아니다.

| DB 또는 HTTP 고객사 격리 실패 | 해당 환경의 출시 중단, 고객 데이터 투입 중단 | 고객사별 DB·전용 연결 역할로 물리 분리하고 인증된 고객사에서 연결을 선택 | 양방향 조회·수정·증빙·외래키·고객사 변조·동시 풀 재사용 전부 통과 |
| 이벤트 유실·부분 반영·재전송 중복 | 새 광고 승인 보류, 성공으로 응답하지 않음 | 원장·상태·outbox의 단일 DB 트랜잭션과 커밋 후 응답, 필요 시 서버 수신 순서 기반 단일 기록 서비스 | 장애 주입 후 전체 롤백, 동시 8건 단일 기록, 프로세스 재시작과 백업 복원 후 원본 대조 |

## 아직 증명하지 못한 것

SOLAPI 실계정 왕복, 고객 공개 사이트의 컨테이너 태그 비교, 운영 인프라의 백업 복원, 고객별 전문 검토, 실제 파일럿 운영과 청구·정산은 미완료다. 결과가 없는 항목을 로컬 PoC 통과로 대체하지 않는다.
