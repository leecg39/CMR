# 한국형 CMP SaaS 설계·구현 계획서

- 작성 기준: 2026-09-30
- 문서 성격: 제품·기술 설계 제안. 법률의견서, 준수 인증서 또는 현재 코드 구현 결과가 아님.
- 요청 자료: 사용자가 제공한 Usercentrics·CatchSecu 비교 및 광고 문자 운영 자료, 첨부 `cmp.md`.
- 자료 구분: 원자료의 개념을 제품의 출발점으로 삼고, 구현에 영향을 주는 규칙은 공식 자료와 대조했다. 기능 범위·스택·일정·지표는 아래에서 제안하는 설계 가정이다.

## 1. 결론과 제품 정의

**웹·회원·메시지에서 개인정보 처리와 광고 전송의 허용 여부를 판단하고, 실제 실행을 통제하며, 그 근거를 증명하는 한국형 동의 운영 SaaS를 만든다.**

쿠키 배너 제작기와 고객 DB를 단순히 합치는 방식이 아니다. 고객사의 CRM·회원·주문 DB는 그대로 두고, 그 위에 공통 동의 원장, 정책 판단 엔진, 웹 태그 차단기, 메시지 발송 게이트웨이를 연결한다.

제품의 세 가지 질문:

1. 이 사용자는 무엇을, 어느 목적·채널·사업자 범위에서 허용했는가?
2. 지금 하려는 추적·광고 발송을 허용해도 되는가?
3. 그 판단의 문구·사용자 선택·규칙·실행 결과를 나중에 재현할 수 있는가?

출시 순서는 **웹 동의와 증빙 → 문자 발송사 한 곳을 통한 집행 → 개인정보 생애주기 연동 확대**로 한다.

첨부 `cmp.md`의 동의 수집, 선호 설정, 감사 기록, 추적 차단이라는 네 기능을 기본 모듈로 유지한다(원문 35–42행). 여기에 한국 광고 전송 운영과 처리 근거·보유기간 관리를 추가한다.

## 2. 원자료와 공식 확인 사항을 구분한 설계 전제

| 원자료의 설명 | 공식 자료 확인 및 보완 | 제품에 반영할 결정 |
|---|---|---|
| Usercentrics는 쿠키만, CatchSecu는 회원 동의만 담당 | Usercentrics도 Preference Management를 제공한다. 기능 영역은 일부 겹친다.[S7][S8] | 한국형 발송 통제와 증빙 연결을 차별화 가설로 삼는다. “경쟁자가 없다”고 가정하지 않는다. |
| 수신거부를 14일 안에 처리 | 거부·철회 후 광고 전송을 중단해야 한다. 14일은 동의·거부·철회에 대한 처리결과 통지 기한이다.[S1][S2] | 철회 반영과 통지 작업을 분리한다. 차단을 통지 완료까지 미루지 않는다. |
| 2년 주기 수신동의 확인 안내 | 2년 주기의 수신동의 여부 확인 의무이며, 단순히 2년이 지났다고 동의가 자동 만료되는 구조가 아니다.[S3][S6] | `notice_due_at`과 `consent_valid_until`을 구분한다. 통지로 동의일을 갱신하지 않는다. |
| 문자 수신거부는 법적으로 080만 가능 | 무료·간편한 거부 방법을 제공하는 것이 핵심이다. 매체별 구체 형식은 별도 검토한다.[S6] | 첫 문자 커넥터는 운영이 명확한 080을 표준으로 선택한다. URL만 있으면 적법하다고 자동 판정하지 않는다. |
| 장기 미접속자는 법에 따라 일괄 파기 | 종전 개인정보 유효기간제는 폐지되었다. 목적 달성·보유기간·별도 보존 근거로 파기를 판단한다.[S4][S14] | “1년 미접속 자동 삭제”를 법정 기본값으로 넣지 않는다. |
| 알림톡과 마케팅 수신 동의를 함께 설명 | 알림톡은 정보성 메시지 상품이다.[S11] | 거래 안내·법정 안내·광고를 구분하고 광고의 알림톡 라우팅을 차단한다. |
| 유럽·북미 방문자라면 Google 인증 CMP 필수라는 체크리스트 | Google 인증 CMP 요건은 적용 제품·광고 유형·지역을 나눠 확인해야 한다.[S9] | Consent Mode 지원과 Google 인증을 별도 기능·출시 관문으로 취급한다. |

개인정보 처리의 적법 근거는 동의만이 아니다. 계약 이행 등 다른 근거와 동의에 따른 처리를 분리해야 하므로 `lawful_basis`와 `consent`를 서로 다른 개념으로 모델링한다.[S4]

KISA가 2026-03-04 게시한 제7차 개정 안내의 주요 사항도 문구 검사에 반영한다. 광고 동의를 “혜택 알림”처럼 모호하게 표시하지 않고, 사업자가 일방적으로 제공한 쿠폰·적립금 등의 발급·소멸 안내를 무조건 정보성으로 분류하지 않는다.[S5]

> 적용 법령·가이드·플랫폼 정책은 서로 다른 규칙 층이다. 특정 요건을 충족했다고 서비스 전체의 적법성이나 광고 플랫폼 인증을 보장하지 않는다. 출시 전 고객 업종과 실제 처리 구조에 대한 전문 검토가 필요하다.

## 3. 초기 고객과 제공 가치

### 3.1 초기 고객 가설

첫 고객군은 국내 웹사이트를 운영하면서 회원가입·이벤트·광고 문자를 함께 사용하는 이커머스·교육·예약·회원제 서비스다. 기존 회원 DB와 문자 발송 계정을 보유하고, SDK 또는 서버 API를 연결할 개발 담당자가 있는 팀을 우선한다.

의료·금융의 특수 규제, 민감정보, 만 14세 미만 대상 서비스, 복잡한 다국가 광고 수익화는 첫 버전의 지원 범위에서 제외한다. 제외 범위는 가입 심사와 계약·제품 화면에 명시하고, 지원하지 않는 고객을 “자동 준수” 상품으로 판매하지 않는다.

### 3.2 구매 이유

- 개발자: 체크박스·배너·수신거부·증빙을 프로젝트마다 다시 만들지 않는다.
- 마케팅 담당자: 보낼 수 없는 사람과 이유를 발송 전에 확인한다.
- 개인정보 담당자: 실제 노출 문구와 동의·철회·발송 이력을 하나의 타임라인으로 확인한다.

핵심 판매 문구는 **“동의를 받는 화면부터 발송 차단과 증빙까지 연결합니다.”**로 제안한다. “과태료 100% 방지”, “설치만 하면 모든 법 준수”는 사용하지 않는다.

## 4. 제품 범위와 우선순위

| 영역 | 첫 출시 범위 | 후속 범위 |
|---|---|---|
| 웹 동의 | 사이트 등록, 도메인 소유 확인, 배너·설정 창, 목적별 허용, 버전 게시 | 모바일 SDK, 여러 도메인의 검증된 계정 연계 |
| 웹 추적 제어 | 등록된 태그의 사전 실행 통제, GTM·Google Consent Mode 어댑터, 실제 브라우저 검증 | 서버사이드 추적·추가 광고 플랫폼 어댑터 |
| 회원 동의 | 임베드 동의 폼, 목적·채널 분리, 검증된 회원 식별 연동 | 오프라인 QR 폼, 복잡한 제3자 제공·국외 이전 관리 |
| 증빙 | 동의 이벤트 원장, 문구 버전, 현재 상태, 타임라인, JSON·CSV 내보내기 | 외부 감사 제출 양식, 선택적 외부 타임스탬프 |
| 문자 통제 | SMS/LMS/MMS 발송사 1곳, 080 연계, 발송 전 검사, 예약 재검사 | 추가 발송사, 이메일, 카카오 광고용 메시지, 앱 푸시 |
| 법정 운영 | 처리결과 통지, 2년 확인 안내, 실패 재처리와 담당자 알림 | 회사별 복잡한 통지 통합·캠페인 연동 |
| 정책 문서 | 검수된 템플릿, 문구 버전, 담당자 승인 후 게시 | 운영 시스템 변경과 연계한 방침 영향 분석 |
| 파기 | CMP 자체 데이터의 보유·삭제, 고객사 외부 삭제 요청 추적 | CRM·스토리지별 삭제 실행 및 검증 커넥터 |
| 기업 운영 | 테넌트·역할·API 키·감사 로그·기본 과금 | SSO·SCIM·전용 환경·대행사 다중 고객 관리 |

문자 발송 플랫폼이나 CRM을 새로 만드는 프로젝트로 확대하지 않는다. 고객사의 기존 발송·고객 시스템을 통제 가능한 인터페이스로 연결한다.

## 5. 두 개의 핵심 사용자 여정

### 5.1 웹 방문자: 등록에서 기술 검증까지

```text
관리자 가입 → 사이트 등록 → 도메인 소유 확인
→ 테스트 페이지 브라우저 스캔
→ 서비스·목적·태그 분류 및 담당자 확인
→ 배너·설정 창·정책 버전 게시
→ SDK/GTM 설치
→ 미선택·전체 거절·부분 동의·전체 동의·철회 상태별 재검증
→ 운영 시작
```

스캔 결과는 발견한 네트워크 요청·쿠키·저장소와 실행 조건을 보여준다. 스캐너가 찾지 못한 코드가 없다고 보장하지 않는다. 실제 사용자 동작이 필요한 태그는 테스트 시나리오에 그 동작을 포함한다.

### 5.2 회원과 문자: 동의에서 철회까지

```text
회원가입/이벤트 페이지
→ 서비스에 필요한 처리 안내와 선택 동의 구분
→ 개인정보 마케팅 이용과 채널별 광고 수신 선택
→ 승인된 문구 버전 + 검증된 주체 + 선택 이벤트 기록
→ 처리결과 안내 작업 생성
→ 광고 템플릿 작성·검사
→ 발송 대기열 등록
→ 발송 직전 최신 동의·거부·시각·내용·발신자 재검사
→ 발송사 접수·결과 기록
→ 080/설정 페이지에서 철회
→ 자체 차단 상태 즉시 반영 + 미실행 예약 취소 + 외부 전파
→ 철회 처리결과 안내 + 증빙 보관
```

쿠키 마케팅 허용을 SMS 광고 수신 동의로 바꾸지 않는다. SMS 동의를 이메일·카카오·다른 법인이나 브랜드에 자동 확장하지 않는다. 실제 동의 문구의 범위를 저장하고 해당 범위 안에서만 사용한다.

## 6. 권한과 동의의 도메인 모델

### 6.1 반드시 분리할 개념

| 개념 | 예시 | 설계 원칙 |
|---|---|---|
| 처리 활동 | 주문 처리, 회원 운영, 맞춤광고, 문자 마케팅 | 어떤 개인정보를 무슨 목적으로 쓰는지 정의 |
| 법적 처리 근거 | 동의, 계약 이행, 법령상 의무 | 고객이 임의 입력한 값만으로 유효성을 인정하지 않음 |
| 개인정보 동의 | 마케팅 이용, 제3자 제공 | 해당 목적·항목·문구·수신자 범위에 연결 |
| 광고 수신 동의 | SMS, 이메일, 카카오 광고용 메시지 | 수단과 연락처, 전송자 범위를 함께 관리 |
| 야간 광고 동의 | SMS 21:00–08:00 별도 허용 | 일반 수신 동의를 대체하지 않는 추가 조건 |
| 웹 추적 허용 | 분석, 광고, 기능 | 브라우저 또는 검증된 계정의 해당 웹 범위에 한정 |
| 서비스 이용약관 수락 | 서비스 계약 조건 | 개인정보 동의와 다른 `agreement_event`로 관리 |

법의 야간 별도 동의 및 거래관계 예외에는 구체적인 매체·조건이 있다.[S1][S15] 첫 버전은 보수적인 제품 정책으로 광고 문자 주간 발송과 명시적 동의 경로만 지원한다. 거래관계 예외를 고객 체크박스 하나로 활성화하지 않는다.

### 6.2 상태

```text
UNKNOWN  : 확인 가능한 의사표시 없음
GRANTED  : 검증된 범위의 유효한 동의
DENIED   : 동의하지 않는다는 의사표시
REVOKED  : 기존 동의 철회
```

증빙 상태는 별도다.

```text
VERIFIED | LEGACY_UNVERIFIED | REVIEW_REQUIRED
```

2년 안내 시점은 동의 만료 상태가 아니다. 실제 처리 목적의 종료·기간 제한은 별도 조건으로 평가한다.

### 6.3 식별자와 연락처

기본 주체는 테넌트 안에서만 의미가 있는 임의 ID다. 익명 브라우저를 IP 주소로 회원과 추정 결합하지 않는다. 회원 연결은 고객사 서버의 검증된 로그인 상태를 통해 수행한다.

전화번호를 계정의 영구 식별자로 삼지 않는다. 번호 변경·재사용, 공용 연락처, 여러 계정의 같은 연락처를 고려해 연락처 이력과 검증 상태를 분리한다. 새 번호로 기존 번호의 수신 동의를 자동 이전하지 않는다.

고객사 간 동일 인물을 추적하는 공통 식별자는 만들지 않는다. 전화번호 조회가 필요한 경우에도 테넌트별 비밀키로 HMAC을 계산하고 원문은 별도 암호화 저장한다. HMAC과 토큰을 사용했다고 자동으로 익명정보가 되는 것으로 취급하지 않는다.

## 7. PostgreSQL 개념 스키마

아래는 테이블 설계 지침이며, 실행·검증된 데이터베이스 마이그레이션 파일은 아니다.

| 테이블/그룹 | 주요 필드 | 주의 사항 |
|---|---|---|
| `tenants`, `memberships`, `roles` | 테넌트, 사용자, 역할 | 테넌트는 인증된 세션에서 결정 |
| `controllers`, `brands`, `sites` | 책임 사업자, 브랜드, 도메인, 환경 | 요금제 테넌트와 법적 동의 범위는 동일 개념이 아님 |
| `subjects`, `identity_links` | 임의 주체 ID, 검증된 외부 ID, 연결 근거 | 서로 다른 테넌트 간 연결 금지 |
| `contact_points` | 주체, 채널, 암호문, HMAC, 검증·유효기간 | 연락처 변경 이력 보존 정책 분리 |
| `purposes`, `processing_activities` | 목적, 처리 항목, 근거, 제공받는 자, 보유 규칙 | 법적 근거와 동의 상태를 혼동하지 않음 |
| `notice_versions`, `published_configs` | 실제 문구, 언어, 버전, 해시, 승인자, 시행 시각 | 게시된 버전 덮어쓰기 금지 |
| `consent_events`, `agreement_events` | 주체, 범위, 이벤트, 문구, 출처, 시각, 순서 | 동의와 서비스 약관 수락 분리 |
| `consent_current`, `suppressions` | 최신 상태, revision, 거부 범위·사유 | 철회 트랜잭션에서 동기 갱신 |
| `rulesets`, `decisions` | 규칙 버전, 입력 요약, 결과, 이유, 평가 시각 | 그 시점의 판단 재현 가능 |
| `notification_jobs`, `message_jobs` | 안내/광고 구분, 기한, 기준 이벤트, 상태 | 재시도 시 중복 발송 방지 |
| `connectors`, `outbox`, `delivery_attempts` | 연동 상태, 이벤트, 전송 ID, 결과 | 공급자 접수와 최종 결과를 분리 |
| `retention_policies`, `deletion_tasks`, `holds` | 보유 근거, 만료 조건, 시스템별 삭제 확인 | 외부 삭제 미확인 상태를 완료로 표시하지 않음 |

### 7.1 동의 이벤트의 최소 정보

```json
{
  "event_id": "evt_demo_001",
  "tenant_id": "tenant_demo",
  "controller_id": "controller_demo",
  "subject_id": "subject_demo_001",
  "contact_point_id": "contact_demo_sms_001",
  "consent_kind": "advertising_reception",
  "purpose_id": "purpose_campaign_sms",
  "channel": "sms",
  "time_scope": "general",
  "action": "granted",
  "notice_version_id": "notice_sms_2026_09_v1",
  "source": "customer_server_verified_form",
  "occurred_at": "2026-09-30T01:00:00Z",
  "received_at": "2026-09-30T01:00:01Z",
  "scope_revision": 12,
  "evidence_status": "VERIFIED",
  "idempotency_key": "demo_signup_submission_001"
}
```

예시는 가상 데이터다. 서버가 테넌트·주체·수신 시각·순서·검증 결과를 결정하며, 클라이언트가 전송한 모든 값을 신뢰하는 API로 구현하지 않는다.

원장에는 승인된 문구와 실제 렌더링 변형을 확인할 수 있는 정보가 필요하다. 해시만 저장하고 원문을 버리면 무엇에 동의했는지 설명할 수 없다. 동적 문구에 개인정보를 삽입할 때는 증빙의 최소 수집 원칙도 적용한다.

### 7.2 데이터베이스 불변 조건

- 테넌트가 포함된 복합 외래키로 다른 테넌트 자원의 참조를 차단한다.
- `(tenant_id, producer_id, idempotency_key)`에 고유 제약을 둔다.
- 현재 상태의 고유 키에는 사업자·주체/연락처·동의 종류·목적·채널·범위를 포함한다. NULL 조합이 중복을 허용하지 않도록 명시적으로 설계한다.
- 클라이언트 시각만으로 최신 이벤트를 결정하지 않는다. 검증된 생성 주체, 서버 순서, 인과관계를 함께 사용한다.
- 이전 동의 이벤트 재전송은 철회를 되돌리지 못한다. 재동의는 새로 검증된 사용자 의사표시여야 한다.
- 원장은 보존기간 안에서 수정 대신 정정 이벤트를 추가한다. append-only가 영구 보관의 법적 근거는 아니다.

### 8.1 추천 구현 형태

처음부터 마이크로서비스로 잘게 나누지 않는다. TypeScript 기반 모듈형 백엔드와 독립 워커로 시작한다. 관리자 UI와 기존 웹사이트는 유지하고 실행에 필요한 동의 코어를 추가한다. 현재 저장소의 코드 구조는 별도 점검 후 아래 경계를 적용한다.

```text
apps/
  console/              # 고객 관리자 UI
  api/                  # 인증·동의·판단·발송 API
  worker/               # 스캔·통지·발송·삭제 작업
packages/
  consent-domain/       # 상태·범위·불변조건
  policy-engine/        # 버전 규칙과 판단 이유
  web-sdk/              # 배너·설정·태그 게이트
  connectors/           # 문자·080·CRM 어댑터
  database/             # 스키마·마이그레이션·테넌트 격리
  evidence/             # 문구·로그·증빙 생성
  test-fixtures/        # 개인정보 없는 합성 시나리오
```

이 폴더 구조는 제안이며 실제 프로젝트에 이미 존재한다고 확인한 것이 아니다.

### 8.2 웹 SDK 구현 원칙

배너가 아니라 실제 태그의 로딩 순서를 통제한다. 등록된 추적 스크립트·iframe·픽셀을 SDK가 승인하기 전에 실행하지 못하도록 설치 방식을 제공한다. 필수 기능과 선택적 추적을 구분하고 미분류 항목은 담당자 검토 대상으로 둔다.

Google Consent Mode는 모든 추적 요청을 차단하는 장치와 같지 않다. Basic과 Advanced는 비동의 상태의 태그 실행과 전송 방식이 다르다.[S10] 첫 기본 프리셋은 사전 로딩을 통제하는 보수적 방식으로 잡고, Advanced는 별도 평가·승인 항목으로 둔다.

Google 연동 시 `analytics_storage`, `ad_storage`, `ad_user_data`, `ad_personalization`을 목적별로 매핑한다. GTM 템플릿은 전용 consent API와 실행 순서를 사용한다.[S16]

철회는 이후의 처리 중단과 접근 가능한 저장소 정리를 포함한다. 이미 외부에 전송된 데이터가 브라우저 버튼 하나로 회수된다고 표시하지 않는다. 서버사이드 이벤트 전송은 별도 어댑터와 검사 대상이다.

### 8.3 스캐너 보안

고객이 소유권을 증명한 도메인만 검사한다. 사설 IP·클라우드 메타데이터 주소·DNS 재바인딩·우회 리다이렉션을 차단하고 격리 브라우저, 요청량 제한, 실행 시간 제한을 적용한다. 실제 고객 비밀번호나 운영 개인정보를 스캔용 브라우저에 입력하지 않는다.

검사 상태는 `검증됨 / 부분 검증 / 미검증 / 실패`로 표시한다. 승인되지 않은 URL을 방문하는 범용 프록시가 되지 않도록 한다.

## 9. 광고 발송 게이트웨이

### 9.1 광고 허용 판정: 첫 버전 정책

```text
광고 발송 허용 =
  해당 개인정보 이용의 처리 근거가 유효하고
  실제 전송자·목적·채널·연락처 범위의 명시적 수신 동의가 있고
  더 최신의 거부·철회가 없고
  현재 발송 시각이 지원 정책을 충족하고
  승인된 템플릿·실제 렌더링 내용이 일치하고
  광고 표기·전송자 정보·무료 거부 수단이 검사를 통과하고
  발신번호·공급자 조건이 충족되고
  최신 상태를 신뢰할 수 있을 때
```

이는 모든 법적 예외를 표현한 법률 공식이 아니라 MVP의 지원 정책이다. 법정 안내·거래 안내는 다른 검수 규칙으로 평가한다. 개발자가 `is_ad=false`만 넘겨 광고 검사를 우회할 수 없도록 한다.

### 9.2 API 초안

| API | 용도 | 보안·정합성 |
|---|---|---|
| `POST /v1/consent-events` | 검증된 동의·거부·철회 기록 | 서버 키 또는 범위 제한된 서명 세션 |
| `GET /v1/subjects/{id}/preferences` | 현재 동의 설정 | 본인 또는 권한 있는 담당자 |
| `POST /v1/decisions` | 발송/처리 가능 여부 사전 확인 | 최종 발송 권한의 영구 토큰으로 쓰지 않음 |
| `POST /v1/messages` | 검수 템플릿 기반 발송 요청 | 게이트웨이에서 최종 재검사 |
| `POST /v1/provider-events/{provider}` | 080·결과 이벤트 수신 | 서명·재전송·순서 검증 |
| `POST /v1/preference-actions/revoke` | 간편 철회 | 서명된 좁은 범위의 링크, 추가 광고 동의 요구 금지 |
| `GET /v1/evidence/{subjectId}` | 증빙 묶음 | 강한 권한 검사·내보내기 감사 |
| `POST /v1/deletion-requests` | 데이터 삭제 요청 | 본인 확인·보존 근거·처리 범위 분리 |

회원 동의를 사이트 공개 API 키만으로 변경하게 하지 않는다. 간편 수신거부와 전체 개인정보 열람·삭제에는 서로 다른 인증 강도가 필요하다.

판정 응답 예시:

```json
{
  "decision_id": "decision_demo_003",
  "allowed": false,
  "reason_codes": ["MARKETING_CONSENT_WITHDRAWN"],
  "ruleset_version": "kr_sms_explicit_daytime_v1",
  "consent_revision": 13,
  "evaluated_at": "2026-09-30T01:05:02Z",
  "subject_id": "subject_demo_001",
  "contact_point_id": "contact_demo_sms_001",
  "message_class": "marketing",
  "message_hash": "demo-content-hash"
}
```

### 9.3 철회·발송 동시성

철회 수신 시 하나의 트랜잭션에서 이벤트, 현재 상태, 자체 거부 목록, 외부 전파용 outbox를 함께 기록한다. 외부 연동 워커가 처리할 때까지 자체 차단을 미루지 않는다.

예약 문자도 요청 당시 동의만으로 보내지 않는다. 공급자 전송 직전 최신 revision·연락처·시각·문구를 재검사한다. 같은 연락처 범위의 철회와 새 발송 승인 사이에 명확한 순서를 부여한다.

이미 공급자에 접수되었거나 네트워크 호출이 진행 중인 메시지는 취소가 보장되지 않는다. 가능한 취소 API를 호출하고, 승인·철회·공급자 접수 시각을 구분해 기록한다. 이 한계를 고객 화면과 운영 계약에 명시한다.

외부 이벤트는 적어도 한 번 전달될 수 있다는 전제로 중복을 제거한다. 발송 결과가 불명확한 타임아웃은 즉시 재발송하지 않고 공급자 접수 여부를 먼저 조회·조정한다.

### 9.4 커넥터 선택

첫 후보는 공개 SMS API와 080 관련 기능을 확인할 수 있는 SOLAPI다.[S12] 이 문서에서는 실제 계정 개설·번호 발급·발송을 수행하지 않았다.

착수 전에 반드시 확인할 공급자 조건은 080 결과의 전달 방식과 지연, 이벤트 서명, 중복 요청 방지, 예약 취소, 상태 조회, 사업자별 거부 범위, 발신번호 등록이다. 공개 API에 080 조회가 있다는 이유로 즉시 웹훅도 있다고 가정하지 않는다.

공급자 자체 수신거부 차단을 함께 사용한다. 즉시 거부 전파나 발송 단계 차단을 검증할 수 없는 커넥터는 경고형 연동으로만 표시하고 실시간 차단 등급을 부여하지 않는다.

### 9.5 예시 문자 템플릿

다음은 구조 예시이며, 실제 상호·연락처·내용으로 검수해야 한다.

```text
(광고) [브랜드명]
고객센터: [운영 중인 연락처]

[승인된 광고 본문]

무료수신거부 [발급받은 080 번호]
```

전송자 정보가 광고 본문 뒤에만 놓이지 않도록 템플릿 구조를 고정한다. 제목이 따로 있는 메시지 유형은 제목·본문 모두에 필요한 표시를 검사한다.[S6]

## 10. 통지·파기·정책 문서 운영

### 10.1 서로 다른 두 통지 작업

| 작업 | 기준 | 저장 정보 |
|---|---|---|
| 동의·거부·철회 처리결과 | 실제 의사표시 이벤트 | 기한, 사실·날짜, 결과, 발송 또는 표시 증빙 |
| 정기 수신동의 확인 | 유효한 수신 동의일과 해당 주기 | 채널별 기준일, 안내 기한, 유지·철회 방법, 처리 증빙 |

법정 기한 계산은 한국 달력 기준으로 구현하고 윤년·월말·시각 경계를 테스트한다. 날짜에 단순히 730일을 더하지 않는다. 안내 문구에 광고를 섞지 않는다. 유지·철회 방법과 무응답 시 처리 방침을 명확하게 안내하며, 명시적 재동의를 요구하는 안내를 보내놓고 응답이 없어도 재동의로 기록하는 방식은 금지한다.[S2][S3][S6]

내부 운영은 법정 최종일보다 앞선 기한을 둔다. 안내 실패는 재시도, 대체 채널의 적법성·정책 검토, 담당자 처리 작업으로 이어진다. 기한이 지난 작업을 단순 삭제하거나 실제 발송되지 않았는데 발송 완료로 처리하지 않는다.

### 10.2 파기는 범위별 실행과 검증

보유기간과 처리 목적, 별도 보존 근거를 먼저 판정한다.[S4] 마케팅 목적의 사용 중단과 주문·결제 자료의 필요한 보존을 구분한다.

```text
대상 산정 → 근거 확인 → 사용 제한
→ 시스템별 삭제 요청 → 실행 결과 수집
→ 검증 완료 / 재시도 / 수동 처리 필요 / 근거 있는 보존
```

전체 고객 DB를 CMP로 복제하지 않는다. 외부 삭제 API가 없는 시스템은 수동 작업과 담당자 확인을 남긴다. 외부 확인 없이 “전사 파기 완료”로 표시하지 않는다.

백업·로그·내보낸 파일·하위 처리 시스템도 데이터 목록에 포함한다. 백업 복구 시 삭제 이력이 다시 적용되도록 복구 절차를 설계한다. 증빙과 거부 유지에 필요한 최소 데이터의 보유 근거·기간도 별도로 검토한다.

### 10.3 정책 문서와 법규 규칙의 변경

문구와 판단 규칙에는 원문 출처, 조항, 적용일, 검토일, 검토자, 승인자, 버전을 붙인다. 변경 시 영향을 받는 기존 목적·동의·예약 발송을 시험한 후 게시한다. 과거 동의 문구를 새 버전으로 덮어쓰지 않는다.

AI는 문구 초안·누락 후보·변경 요약을 보조한다. 최종 적법성 판단, 메시지 분류 승인, 법규 규칙 게시, 삭제 실행 승인 권한을 AI에 단독 부여하지 않는다. 실제 고객 개인정보를 기본적으로 외부 생성형 AI에 보내지 않는다.

## 11. SaaS 보안과 서비스 운영

### 11.1 테넌트 격리

PostgreSQL RLS와 애플리케이션 권한 검사를 함께 사용한다. 테이블 소유자와 우회 권한 역할은 RLS를 우회할 수 있으므로 운영 앱에는 비소유자 역할을 사용하고 적절한 FORCE RLS 및 격리 테스트를 적용한다.[S13]

브라우저가 보낸 `tenant_id`를 신뢰하지 않는다. API, 백그라운드 작업, 내보내기, 객체 저장소 경로, 장애 대응 도구까지 같은 테넌트 경계를 검사한다.

### 11.2 역할

- 소유자: 계약·결제·관리자 초대·최고 권한.
- 개인정보 담당자: 문구 승인, 법규 규칙 검토, 증빙, 권리 요청.
- 마케팅 담당자: 승인된 템플릿·발송 요청. 동의 원장 수정이나 원문 연락처 일괄 조회는 금지.
- 개발자: 사이트 설치·API·연동 상태. 필요한 범위만 접근.
- 감사 열람자: 읽기 전용, 내보내기는 별도 승인.

관리자 MFA, 최소 권한 API 키, 키 교체, 서명 웹훅, 로그 마스킹, 감사 내보내기, 취약점 점검, 백업 복구 훈련을 출시 관문으로 둔다.

### 11.3 개인정보 처리 구조

고객사와 SaaS 사업자의 실제 역할, 위탁·재위탁, 데이터 위치, 외부 발송사, 지원 도구와 로그 전송을 목록화해 계약과 방침에 반영한다. 국내 리전 사용은 제안 운영 선택이지 모든 법률 검토를 면제하는 조건이 아니다.

테스트에는 합성 데이터만 사용한다. 개발·테스트·운영의 키와 데이터는 분리한다. 유료 고객 해지 시 내보내기, 잔여 보존 근거, 삭제, 거부 목록 이관을 운영 절차로 제공한다.

### 11.4 장애 정책

동의의 현재 상태를 신뢰할 수 없으면 선택적 추적과 광고 전송을 허용하지 않는다. 회원 로그인·주문·결제 같은 필수 기능은 광고 동의 서비스의 장애와 분리한다.

철회 수신 경로는 독립적으로 내구성 있게 운영한다. 철회를 안전하게 기록하지 못한 장애에는 성공 화면을 표시하지 않고 발송 중지·운영 경보를 연결한다.

## 13. 기존 고객 데이터 이관

CSV에 `marketing_agree=true`만 있다고 검증된 동의로 취급하지 않는다. 동의 일시, 문구·범위, 수집 경로, 철회 이력을 받아 검증 수준을 구분한다.

이관 절차:

```text
스키마 매핑 → 중복·형식 검사 → 수신거부 목록 우선 병합
→ 동의 범위·증빙 검토 → 결과 미리보기
→ 담당자 승인 → 일괄 등록 → 차단·허용 샘플 검증
```

증빙이 부족한 항목은 `LEGACY_UNVERIFIED`로 보관하고 첫 버전 광고 발송 대상에서는 제외한다. 동의를 새로 받으려는 연락 자체가 허용되는지도 별도로 검토한다. 임의의 과거 동의 날짜를 생성하지 않는다.

### 제안 운영 목표

다음 수치는 검증 목표이며 현재 성능이나 계약상 SLA가 아니다.

- 같은 리전의 판단 API p95 100ms 이하를 목표로 부하 시험.
- 통제된 경로에서 철회 반영 뒤 새로 승인되는 광고 발송 0건.
- 고객 한 명의 증빙 묶음 생성 1분 이내 목표.
- 거부 외부 전파 지연을 측정하고 커넥터별 보장 범위 공개.
- 법정 통지의 기한 내 처리 여부와 실패·초과 사례를 별도로 표시.

전체 광고 전송 중 게이트웨이를 통과한 비율과 웹 태그 검증 범위를 측정한다. 외부 콘솔에서 직접 보낸 문자는 통제했다고 주장하지 않는다.

## 16. 상품화와 비용 구조

가격은 경쟁사 가격을 모방해 확정하지 않는다. 첫 10개 고객 인터뷰와 2–3개 파일럿에서 도입 비용·운영 절감·연동 난이도를 검증한다. 아래는 상품 구조 제안이다.

| 상품 | 가치 | 주 과금 단위 |
|---|---|---|
| Web | 웹 동의·태그 검증·증빙 | 사이트 수, 처리 트래픽 |
| Growth | 회원 동의·문자 통제·법정 통지 | 관리 주체 수, 판단/작업량, 연동 수 |
| Enterprise | 복잡한 조직·보안·전용 운영 | 조직 범위, 환경, 계약상 지원 수준 |

문자 발송 비용·080 비용·전용 구축·전문 검토는 구독료와 분리해 표시한다. 고객의 메시지 예산 상한과 발송량 경보를 둔다.

철회·거부 기록, 필수 증빙, 필요한 기본 보안은 비싼 플랜에만 두지 않는다. 요금 초과 때 광고 발송은 제한할 수 있지만 수신거부 기능을 막지 않는다.

주요 원가는 브라우저 스캔, 발송·통지, 데이터 보관·백업, 외부 연동 지원, 보안·법규 유지보수다. 페이지 전체 스캔과 무제한 증빙 저장을 정액으로 무제한 제공하지 않는다.

## 17. 출시 전에 확정할 운영 결정

- 실제 공급자 1곳과 080 차단·전파 동작, 접수 후 취소 범위.
- 지원 고객 업종·국가·채널과 지원하지 않는 동의·처리 유형.
- 목적별 문구, 처리 근거, 보유·삭제 규칙, 증빙 보유 기준.
- 고객사와 SaaS·발송사 사이의 처리 역할·계약·접근 권한.
- 외부 발송 우회, 설치 누락, 서버사이드 추적 등 통제 밖 범위의 표시 방식.
- 장애 시 광고 보류, 철회 접수, 기한 임박 통지와 수동 대응 책임자.

**첫 출시의 합격 기준은 ‘배너가 보인다’가 아니다. 사이트 설치 → 선택에 따른 추적 통제 → 회원 문자 동의 → 발송 가능 확인 → 철회 → 다음 발송 승인 차단 → 전체 근거 내보내기까지 한 흐름으로 검증되는 것이다.**
